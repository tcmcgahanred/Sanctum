# Changelog — Sanctum

Notable changes to the Sanctum intelligence apparatus. **Git is the source of truth**; this file is the curated-highlights layer and `git log` is the full record. Brief editions (Vox) are keyed by distribution date (`vYYYYMMDD`), separate from code versioning.

## [2026-08-25] Two vox standards moved out of the analyst's head and into the document

Vox Policy §5 and §6.2 were rules a person had to remember. They are now annotations on the staging document, and §8's production gate is an artifact the pipeline emits rather than a checklist someone keeps. **All three are advisory: nothing here touches a score, a tier, the ordering, or the surface-vs-drop decision.**

- **`[NO BODY]` marks a candidate with no usable article text.** Policy §6.2 says an entry is written from the body, never the headline, and an item with no body is dropped or its body fetched. Until now nothing showed which items those were — the analyst had to notice. The floor is 40 words of extracted text, configurable, roughly two sentences: enough to tell a real article from a feed stub or a failed extraction, low enough not to flag a terse advisory.
- **Every candidate carries a suggested section**, matched from an ordered list of rules in `cti/pnd.md` using the same grammar as the scoring — `group`, `any`, `all`, `proximity`, `not`, `always`. First match wins. **The engine does not know what CTI's sections are**, which is the point: S2 will declare its own and share the code unchanged.
- **A trailing `?` means the suggestion is weak** — it fell through to the catch-all, or the item has no body and the guess came from a headline alone.
- **NEWS is declared twice, deliberately.** The first entry is a positive match — something happened to somebody — and gets a clean tag; the second is the catch-all and gets the `?`. Without the split every NEWS item would carry a `?` and **the marker would stop meaning anything**.
- **KEYWORDS is not a section candidates get assigned to.** Policy §5 describes it as wave-top only — vendor and sector names, not items — so it is a summary block the analyst writes. It is excluded from the tagger and still checked for presence by the compliance report. Recorded because the reasoning is not obvious from the section list alone.
- **New group `ttp`** for tradecraft language — lateral movement, living off the land, web shell, ATT&CK. It feeds no tier, no multiplier and no force-surface rule, so a false match costs a section suggestion the analyst overrides and nothing else.
- **The §8 production gate is now an emitted artifact.** `compliance_report.md` is written beside the staging document every run and pushed with it. The pipeline pre-fills what it can count — articles scored, candidates surfaced, distinct events, force-surfaced below the cut, STALE, no-body, drop-list size, and candidates per section. **The fields only a person can answer are left blank on purpose**: bodies read, entries written, exclusions with reason, drop list reviewed. A number the machine invented there would defeat the gate. The fourteen edition-level checks come from `cti/pnd.md`, not the engine, each citing its policy section.
- **A zero in the section table is called out in words**, because an empty section that is *deliberately* empty and one that was *forgotten* look identical in a finished document.
- **The fuzz test was measuring the wrong thing, and adding one advisory group exposed it.** `ttp` feeds no rule, yet `diff_scores.py` reported **428 mismatches** — because the fuzz built its token pool from the live config, so a new group changed every generated article. The scoring model had not moved: all twenty hand cases and all fourteen requirements passed throughout. **The baseline now stores the token pool it was generated with**, and the test compares against that, reporting vocabulary drift as a note rather than a failure. **A test that fails whenever the vocabulary grows teaches people to re-baseline reflexively, which is precisely how a real regression gets waved through.**

### Two clauses in the Vox Policy have gone stale — flagged, not changed

Both are Planning & Direction decisions under §9 and are recorded here rather than edited.

- **§7's interim clause is obsolete.** It reads *"Interim (until the pipeline implements M1–M3): the analyst applies the mandatory-surface rule by hand."* The pipeline implements all three and has since the force-surface work. That sentence now asks the analyst to duplicate a guarantee the engine already makes.
- **§5 declares four sections; the section tagger covers three.** `KEYWORDS` is excluded for the reason above. If P&D intends it as a destination for items, the tagger needs a rule for it.

## [2026-08-24] Scoring precision: the sector must be the subject, not a word in the article

Two Planning & Direction work orders in one day. The first tightened matching after the staging queue's top filled with false positives; the second approved the vocabulary that stops the tightening from creating misses. **Nothing was weakened - M1, M2 and M3 all still fire. What changed is what counts as a match.** On the live corpus: 496 surfaced items became 94.

- **The root cause was one ordinary English word.** `water` was a `sector` term, so any article containing it anywhere took tier 2, weight 4.0. An Australian hotel with a water park scored 15.21; a Comcast release mentioning a water-cooled data centre scored 11.70. **A common noun cannot carry a sector requirement.** `sector` and `ci` were rewritten to compound terms. Nine bare terms out, twenty-five precise ones in, no requirement dropped.
- **The subject discipline already existed and had only ever been applied to one tier.** Tier 1 has required California to be the *subject* of an incident since August; tier 2 was still `sector` anywhere in the body. It now uses the same shape, and so does M3.
- **Exclusion by headline shape, using an operator that already existed and had never once been used.** The `not` atom was built in August for term collisions. A new `listicle` group matches shapes that are never incident reporting, and every rule now carries `not listicle`.
- **Four engine additions.** `proximity` gained an opt-in `scope` and `all_occurrences`. A `source` scope exposes the article's origin rather than its content. And **score floors**: a floor raises a score to a minimum, never lowers one, and never forces the surface - deliberately weaker than force-surface, for signals that are authoritative but of unproven relevance.
- **The corpus re-score caught a regression the tests could not, and that is the lesson of the day.** The new proximity code stripped whitespace from its search term, which looked like tidying. `geo` carries the padded terms `' calif '`, `'uc '` and `'csu '`, and **that padding is the word-boundary guard at that call site**. Stripped, a bare `uc` matched by substring inside "product", "reduce" and "structure", and **force-surface rule M1 fired on 190 articles with no California content at all**. The self-baselining test reported PASS throughout, because the baseline was generated *after* the defect existed. **A snapshot proves nothing about the snapshot.**
- **Then the corpus caught a second class of error: fixtures written by whoever wrote the rules.** The reconstructed Siemens advisory contained *"actively exploited"* and a CVE, so it passed at 9.0. The real CISA advisory is headlined *"Defending Against an Active Threat to Siemens S7 Series PLCs"* - and `exploit_strong` had no *"active threat"*. It fell to 1.5, two tiers below where the work order required it. Fixtures are now labelled RECONSTRUCTED or OBSERVED, and the observed ones carry the published headline verbatim.
- **Word order and plurality are not details.** *"Hackers Release Stolen Data From State's Largest School District"* - a California school district breach, PIR-1 dead centre - matched `school district` in the title and then failed for want of an incident word, because the group held `hacked` (not "hackers") and `data stolen` (not "stolen data").
- **Availability language was deliberately kept out of tier 1.** `outage`, `denial of service` and `ddos` went into `targeting`, not `incident`, because `incident` plus a place name is all M1 needs - and California has public safety power shutoffs and wildfire outages every summer. Tested both ways: a planned California outage scores 1.0; a school district taken offline by denial of service takes tier 2.
- **A CISA directive about a product not on the low-maturity list now floats to the surface line rather than sinking.** TrueConf fell from 11.70 to 1.00 under the tightened rules - a real directive, an unlisted product. It is floored to 2.0: visible for review, not force-surfaced. **The floor requires the authoritative feed itself**; The Register's write-up of the same directive scores 1.0 and stays down, which is tested.
- **Two feeds stopped losing items entirely.** Before the vocabulary went in, `cisa.gov` was losing one item in four and `californiacitynews.org` two in seven. Both are now absent from the removal table. That is the fix confirmed on real articles, not fixtures.
- **`geo` does not cover the whole state, and that now shows.** *"El Cerrito Blackmailed by Notorious Cyber Gang"* still cannot surface: El Cerrito is in Contra Costa County, which is not among the 34 counties in `geo`. **The failure is geographic, not lexical.** Recorded unresolved.
- **The parity test was re-baselined, not deleted.** It had compared the engine against `tests/old_arbites.py` to prove the port changed nothing - a job long finished. It now checks fourteen named work-order requirements as assertions, twenty hand cases and 500 fuzz articles against a committed baseline. `old_arbites.py` deleted; git holds it.
- **`tools/rescore_check.py` added**, and it has now caught two defects the suite passed. **Run it before every scoring commit.** The started-surfacing list is the one to read: 190 meant a bug, 5 means the fix held.
- **The Register removal rate is 92% - 47 of its 51 items.** It was added the same morning on a citation audit, which measures whether an outlet breaks stories, not whether its output fits this portfolio. **Not pruned:** P&D wants one or two more cycles to see whether its surviving hits are unique.

## [2026-08-23] Four vendor telemetry feeds, and the one that cannot be collected at all

- **The argument for these is access, not quality.** Vendors running incident response and global sensor networks see things this effort never will. When they publish, it is primary source; the marketing overhead is the price of admission and the scorer sorts it out. Eleven such feeds were already collected — Unit 42, Securelist, Sophos, CrowdStrike, Recorded Future, Tenable, Rapid7, GreyNoise, Qualys, ZDI, Project Zero — so the principle was already the design. **Four names were missing from it**, and they were found by asking the question about a trade publication and then noticing the question pointed somewhere else.
- **A trade publication was refused and its subject added instead.** SC Media was the candidate. It is competent original reporting, but it is journalists covering vendors — and this repo already collects most of those vendors directly, which makes the publication a slower second copy. **The useful move was auditing which vendors it covers that were not collected, then adding those.**
- **Huntress is the strongest fit and not for the obvious reason.** Its output lands on vocabulary this domain already declared: `n-able`, `n-central`, `kaseya`, `connectwise`, `screenconnect` in `lowmat_tech`; `rmm`, `msp` in `supplychain`. Those terms are there because managed-service and remote-management compromise is how a small government organisation actually gets hit, and Huntress's telemetry is made of exactly that. **When a candidate matches word lists written months earlier for unrelated reasons, that is convergent evidence, not coincidence.**
- **Its 680-item feed window is a one-time intake, not a rate.** The whole blog archive is served on every fetch. That is the MSRC *shape* without the MSRC *problem*: MSRC enumerates every CVE forever, while a back catalogue is fixed and steady state falls to a few items a week. The denominator lesson running the other direction — a large `returned` is not automatically a large cost.
- **A live URL serving nothing was caught before loading.** `cloud.google.com/blog/topics/threat-intelligence/rss` returns HTTP 200 with zero entries. Status code said healthy, item count said empty. Loaded on the status alone it would have claimed coverage of Mandiant's reporting and delivered none. The `cloudblog.withgoogle.com` host was taken instead.
- **Two vendors already had a feed here that is not this one.** Cisco's PSIRT advisories are disclosures; Talos is investigation. MSRC is the patch catalogue; Microsoft Threat Intelligence is research. **Having a vendor in the list is not the same as having its intelligence.**
- **Dragos publishes no RSS at all** — ten paths tested and recorded so nobody repeats the search. It is the only one of the five covering the water, wastewater and utility sectors this domain names, so the gap is a real one. **It is blocked on the same engine defect as Cal-CSIC:** `process_page` never revisits a page source. That fix now has a second use case forcing it, which is the bar this repo sets before building anything.

## [2026-08-23] The scrub check removed — a per-user secret was a precondition for using the engine

- **It demanded a local file before any clone could commit.** `scrub_check.sh` compared staged content against `.scrub-denylist`, a list of terms the operator must never publish. That list is deliberately git-ignored, so it does not exist in a fresh clone — and the check fails closed, refusing rather than waving anything through unchecked. **Verified against a clean clone of `main`: with the gate installed and no denylist authored, every commit is blocked.**
- **The decisive argument was not convenience.** Anyone cloning Sanctum would have to invent their own denylist before the commit gate would let them work — a setup burden with nothing to do with what Sanctum does. Worse, it put user-specific configuration outside `pnd.md`, and the whole premise of this repo is that everything specific to a user or a subject lives in one file the engine reads. **A check that only works once you have configured a secret is not a property of the engine; it is a property of one person's install.**
- **Tenet 8 is unchanged.** Nothing identifying goes in the repo. It is now kept by the person committing rather than by a script, which is what the operator asked for and what the architecture already implied.
- **Every reference was inventoried before deletion, not after.** Nine live mentions across seven files: the commit gate's header, its install block and its call; `core/README.md`'s install instructions and its count of checks; `docs/EXPLOITATION.md`, where the scrub check was named as the last line of defence before a vox is published; and four comments in `vocab_check.py` and its test that justified warning-instead-of-blocking on the grounds that `--no-verify` would disable the scrub check too. **That last set is the reason inventory matters** — the reasoning survives, the named check does not, and left alone those comments would have cited a file that no longer exists.
- **`docs/EXPLOITATION.md` gained a real instruction where it had a reassurance.** It used to say the gate would catch anything unintended in a vox. It now says to read the vox before pushing, because that reading *is* the last line of defence and it is a human one.
- **The `.gitignore` rule stays, deliberately.** Anyone who authored a `.scrub-denylist` while the check existed still has one on disk, and removing the ignore rule would make the one file that must never be committed suddenly committable. The line now carries a comment saying so, because it otherwise looks exactly like the leftover tenet 7 says to delete.

## [2026-08-23] Three sensors added, and a drop note that had gone half-wrong

- **A roundup's citation list is a free survey of somebody else's source diet.** Auditing the ten stories a CyberWire daily roundup linked showed five came from The Register and SecurityWeek — neither collected here. That is not an opinion about what is worth reading; it is evidence from someone whose whole job is curating the day's cyber news. **Both added.** The method generalises: when a source is refused, its bibliography may still be worth reading.
- **Feed variants were compared rather than assumed.** SecurityWeek's Feedburner path returns identical content behind a 302 — the first-party path was taken instead, since a Feedburner dependency buys nothing. The Register's whole-site feed leads with git tooling and Microsoft trivia while its security section leads with a CISA patch directive; the section feed was taken and the reason written beside it, because the two paths differ by one word and the wrong one looks correct.
- **SecurityWeek's feed window holds only 10 items**, which is safe solely because collection runs daily — confirmed by counting log entries per day rather than assuming a cadence. Written into the sensor list, because if the schedule ever slackens this sensor loses articles with no error anywhere.
- **California City News added with its low yield stated as the reason to keep it**, not buried. Twelve items in three and a half years, so a column of `0 new of 12 returned` is this sensor working correctly. Nothing else here emits a named California municipal victim, and its local-government policy coverage — closed-session law, grant programs — is invisible to a general news query. Yield review dated in the file.
- **The CyberWire drop note was half wrong and is corrected.** It recorded that the publisher advertises no feed; a live one does exist and publishes daily. The refusal stands on a better reason: every item is a multi-story roundup that would fire four scoring groups at once, outrank real single-event items, and offer nothing citable. **A drop note that records the wrong reason invites the same investigation again in three months** — the correction is the deliverable, not the verdict.

## [2026-08-23] A fourth guard, and the first sensor that names the victim

- **Three changelog entries were written, reported written, and never reached the file.** The scripts that wrote them printed "ok" whether or not the text they were replacing existed. Nothing noticed for days. The entries were restored on 2026-08-22; this is the guard that stops it recurring.
- **`tests/changelog_check.sh` is deliberately dumb.** It does not read the changelog, judge the entry, or care what it says. It asks one thing: you changed something, did you write it down? A smarter check would need maintaining, and the failure it prevents is not subtle.
- **It never blocks — exit is always 0**, and the commit gate calls it with `|| true` on top of that. A warning you can ignore is the right weight for a habit; a gate that stopped a commit over a missing note would be bypassed within a week and then ignored entirely. Published editions and collected material are exempt — a changelog entry for an edition is noise.
- **The commit gate stopped citing tenet numbers.** Its header named tenets 11, 3 and 8 — numbering that died when the doctrine went from eleven rules to eight. The rules are now stated in words. **A number restated in a second file is a number that goes stale in one of them**, which is the ownership rule the domain contract already enforces, applied to a script header nobody thought to check.
- **Have I Been Pwned added as a sensor** — `haveibeenpwned.com/feed/breaches/`. Around two or three items per cycle, first-party, and the only source in the list that emits a named victim organisation with a record count. Consumer web-service breaches fall to the bottom tier and drop on their own; a district or county in the registry takes a top tier without any tuning.
- **Its known limit is written beside it in the sensor list.** The feed's item date is the date a breach was *loaded*, not the date it happened, so a years-old breach loaded yesterday arrives looking new and the recency gate will not flag it. That is an inversion of the gate rather than a way around it, and the mitigation is one glance: every description opens with the month the breach actually occurred. **A sensor with a known failure mode is fine; a sensor with an unwritten one is not.**

First full health check from the collector host. 50 sensors in, 47 returning items, 3 not — and one that had been reported dead was healthy.

- **A status code proved nothing, exactly as designed for.** All three failures returned 200 or followed a redirect cleanly. Only the item count exposed them.
- **Packet Storm** — the site moved to a new domain and every feed path 404s there, including on its dedicated feed host. Already at 1 new in 9 runs before the move.
- **Full Disclosure** — reachable, but not by this collector. `curl` gets 200 from the same host on the same machine; `feedparser` gets connection-reset every time, under its default user agent and three others. The difference sits below the user agent, in the HTTP client itself. **Recorded rather than fixed:** swapping the fetch layer is not worth it for one sensor, and writing it down stops the next person repeating the user-agent experiment.
- **MS-ISAC advisories** — broken at the publisher. Returns 200 with an "Object moved" stub pointing at an internal URL that serves a web application rather than a feed. Coverage survives through the sibling alert feed. This one had been claiming active area-relevant coverage while serving an HTML stub.
- **Fortiguard was reported dead and is not.** The incoming report recorded HTTP 500 with an error page; from the collector host it returns 50 items behind a redirect. **Nothing was removed on the strength of that report.** Diagnose before deleting — a sensor removed on a guess is one someone re-adds next year.
- **MSRC returned 4,912 items in a single fetch**, around three quarters of everything pulled. It is not publishing 4,912 new articles; it serves its whole catalogue every time and dedupe reduces it to a handful. That is the gap between *returned* and *new* made visible, and it explains the old "52.7% of the corpus" figure — the first fetch saved the entire catalogue as new.

## [2026-08-19] Sensor health: count the items, not the status code

Findings from the second subject's first five cycles. Two of the four requests were corrected before building — one would have fixed nothing.

- **A sensor can be configured, listed, and contributing nothing, with no error anywhere.** The run completes, the item count is quietly lower, and the sensor list claims coverage that does not exist.
- **Per-sensor counts already existed and were counting the wrong thing.** The collector logged `"<url> -> N new"`, where N is articles kept *after* the already-seen filter. A feed returning fifty items you have all seen logs `0 new`, identical to a dead one. The number that separates them — how many items the source returned at all — was computed every run and discarded. **Second time a count without its denominator has misled here**; the first was match-frequency in the archive search. When reporting a count, report what it is out of.
- **The silent reclassification was the actual mechanism.** A feed parsing to zero entries returned nothing and the caller fell through to the page-collection path without comment, so a broken feed quietly became "a page source that yielded nothing." It still falls through — sometimes a page is the right path — but it now says so.
- **The redirect request was declined; the diagnosis was wrong.** feedparser already follows redirects — tested against a known 301, which it followed while reporting both the status and the final URL. The failing sensor's problem was a 403 at the destination. Building redirect-following would have fixed nothing while appearing to fix something.
- **`tools/sensor_check.py`** — fetches every sensor a subject declares and reports items, status, redirect chain, parse result and a verdict. Items first: a feed flagged malformed can still yield usable entries, and a first crude pass produced three false alarms that way.
- **A guard found by using the tool on itself.** Run from a sandbox behind an egress proxy, all four sensors returned an identical 403 including two that are certainly healthy. Read literally, that output says "delete four working feeds." The tool now detects a uniform failure across every sensor and says the problem is the machine you are running from.
- **The multiplier ceiling check.** A subject documented its multiplier stack as 4.9x; six signals actually multiply to **6.43x** — five factors had been multiplied instead of six. A floor-tier item with every signal then outranked every mid-tier item in the cycle. The vocabulary guard now computes the product and compares it to the gap between the top tier and the one two steps down. **It flags the miscalculated figure as an error too** — the check does not depend on anyone getting the arithmetic right first.
- **A group's own name used as a term** is now flagged. Harmless at runtime, misleading on review — it inflates the term count and reads as real coverage.
- **Two design lessons written into `VOCABULARY.md`, both learned by reading output rather than by any check.** A group mixing specific designations with category nouns will surface your own side's stories while passing every automated test. And bare co-occurrence across a whole article body is barely a condition — observed false positives matched one generic word and one platform word paragraphs apart. Proximity is now the documented default for multi-group conditions.
- **Proximity's three unguessable behaviours documented at last.** Body only, never the title; only the first occurrence of each anchor-side term is tested; and the anchor side has no word-boundary protection while the other side does. That last one bit in production.

## [2026-08-17] `DOMAINS.md` — what a domain folder is, and who owns which fact

- **The engine requires exactly one file from a domain: `pnd.md`.** Nothing in `core/` opens anything else in a domain folder. That was already true and nothing said so, which meant `cti/` was being read as a template when it is actually one domain's history — design and accident mixed together, with no way to tell which was which.
- **The folder contract, written down.** `pnd.md` required; `vocab.md`, `README.md`, `decomposition.md`, `mandate.md` expected; `policy.md` and `editions/` optional and only for domains that produce a product. ## [2026-08-16] Lexicanum — archive search and match-frequency over time

- **The corpus was write-only.** Sanctum scores each cycle independently and then forgets, keeping every article permanently while offering no way to ask the archive a question. Trend is the stated reason for retaining everything, and it was the one thing the tooling could not do.
- **The workflow being replaced was manual.** Bulk keyword search across a pile of documents, hits pasted into a spreadsheet with a column naming the term that matched. The term was not a filter but an **index** — a handle to pull later. Question one: *where has this appeared?* Question two follows immediately: *is it actually spreading, or is one event being re-reported?* Those call for different responses. Search and counting are the same feature, which is why they shipped as one engine rather than two.
- **`core/lexicanum.py`** — searches the whole archive by keyword group or ad-hoc term and reports a per-period series alongside the items behind it. `--group` (repeatable), `--all-groups`, `--term`, `--since` / `--until`, `--by day|week|month`, `--by-published`, `--counts`, `-o`, and `--pnd` for out-of-tree domains.
- **Matches are recomputed on demand, not stored at collection time.** This is the design, not a shortcut. A stored index can only answer questions you thought to ask on collection day; because full text is retained and the matcher is deterministic, **a group invented this morning runs against everything collected last year** — including terms for a system nobody was tracking when the articles arrived. It also guarantees results agree with the scorer: same matcher, same word-boundary rules, same scopes, no second implementation to drift. Verified by test.
- **Reports a RATE, not a bare count — added after the first real run nearly misled.** Weekly ransomware hits fell 475 → 122, which read as a collapse. Article volume that week had fallen 6,585 → 1,370, so the rate had actually *risen*, 7.2% → 8.9%. Counts alone said the opposite of the truth. Every table now carries the period's article total as an `of` column and a `rate` column, the bar tracks rate rather than hits, and collection volume per period is stated once at the top. Regression-tested with the same shape at small scale: 20 hits of 100 versus 2 of 10 — a 90% apparent collapse at a flat 20% rate.
- **Bucketed on collection date.** Publication dates are missing or malformed often enough that the scorer carries an entire recency gate to cope; bucketing on a frequently-absent field would produce a clean-looking chart built on guesses. Each hit still shows its publication date, and `--by-published` switches axis, falling back per-item and reporting how many items it had to fall back on.
- **Reports counts, never conclusions** (tenet 9). The header states plainly that reporting volume is not activity — a quiet week for a publisher looks identical to a quiet week in the field. Every count is backed by a listable item, so no number appears that cannot be drilled into (tenet 8). A group with zero hits is reported as zero rather than omitted: mistargeted and genuinely quiet are different findings and both are worth seeing.
- **Groups with no hits are the staleness signal.** This supersedes the separate vocabulary-staleness request, which asked for a review-date flag. A group that has matched nothing across many cycles is empirical evidence of decay, where a calendar date is only a reminder.
- **Read-only.** It writes nothing to the corpus, changes no score, and is not part of the weekly cycle — it runs when asked.

## [2026-08-16] Exclusion operator — "match X unless Y"

- **Deleting a noisy term silently deletes the requirement it stood for.** With no way to express an exception, the only cure for a term that collides with an unrelated meaning was to remove it. Threat-actor names are the standing example: several are also ordinary products, places, or common words, and they arrive through general feeds that are otherwise wanted — so dropping the *source* was not available either. Every collision so far was resolved by finding a more precise synonym; where none exists, the choice was accept the noise or lose the requirement. This is the third option.
- **`not` added to the rule grammar.** `{all: [{group: X}, {not: {group: Y}}]}`. Composes with `any`, `all`, `proximity` and itself; usable in tier rules and multipliers alike.
- **Narrow, deliberate exception to tenet 8** ("prefer false positives — flag, don't drop"). Exclusion removes nothing: it withholds a tier or a multiplier, so an excluded item is still collected, still scored, still listed in the drop list, and still shown with its reasoning — just lower. Tenet 8 in the README now records this explicitly.
- **A satisfied exclusion names itself in the scoring reasoning** (`not medical`), because an auditor reading a score needs to see that the exclusion fired, not merely which terms hit.
- **Config validation recurses into `not`.** A typo inside an exclusion would otherwise reference a group that does not exist, match nothing, and silently switch the exclusion off — letting the noise back in with nothing on the page to say so. Unknown groups inside `not` now fail at load.
- **Verification.** `tests/upgrades_test.py` — a name collision resolves correctly, double negation and nesting behave, the excluded article falls to the floor rather than disappearing, and **a config containing no `not` scores exactly as before**. Backed by the full parity suite: **514/514 real articles and 500 fuzz articles match the pre-change engine exactly**, so no existing edition moves.

## [2026-08-16] Tenet 3 rewritten; domain files enforced inert

- **Tenet 3 was about the wrong thing.** "Config over code — steer by editing `pnd.md`, never by editing Python" named a *file format* when the property that actually matters is *separation*: the engines learn nothing about a domain, so a new domain is a drop-in and performs the same as any other. Format was never the point; it was one way of protecting the point.
- **Rewritten as the guardrail it always was.** Tenet 2 now states the goal (domain-agnostic engine, same performance on any domain). Tenet 3 states the constraint that preserves it: *domain files declare, they never behave* — settings and the explanation of those settings, nothing else.
- **Why this came up.** Moving domain files from YAML-inside-markdown to Python puts each explanation directly against the setting it describes, instead of in a prose section that drifts away from it. That drift is not hypothetical here: a wrong explanation of a dead sensor once propagated into three documents at once. The gain is real, but YAML's inability to express logic was also an accidental guard, and Python hands that ability back.
- **So the tenet no longer relies on discipline.** `tests/domain_check.py` parses each domain file and refuses anything that is not inert data: imports, functions, classes, conditionals, loops, calls, lambdas, comprehensions, attribute access, subscripting, f-strings, arithmetic, and references to names not defined earlier in the same file. Permitted: literals, nestings of literals, comments, a docstring, and a reference to a value assigned above — so a shared term list is defined once rather than retyped into two groups that later disagree.
- **Deliberately stricter than necessary.** Some refusals are harmless in isolation — joining two lists with `+` computes nothing dangerous. Strictness is cheap to relax when a real need appears and expensive to reimpose after a domain file has grown a brain (tenet 10).
- **Messages are written for a non-programmer**, because whoever stands up a domain should not need to be one: *"a condition makes the file act differently in different situations."*
- **`core/pnd.py` is excluded by name.** It is the engine that *loads* domain files and is legitimately full of logic — same filename, opposite meaning.
- **New commit gate.** `tests/pre_commit.sh` now runs both guards (scrub, tenet 11; domain, tenet 3) and is what gets installed as the hook; `scrub_check.sh` is no longer installed directly. Both guards run even when the first fails, so one commit attempt reports everything wrong at once.
- **Verification.** `tests/domain_check_test.py` — a realistic clean domain file passes untouched, and **28 forms of behavior are refused**, including three nested inside literals, each with a plain-language reason. Discovery over the live repo correctly finds `cti/pnd.md` (skipped: YAML cannot express logic) and correctly ignores `core/pnd.py`.
- **No engine change and no domain file converted.** This lands the guardrail first; the markdown-to-Python migration is a separate, later change that this makes safe.

## [2026-08-13] Same-event grouping in the staging report

- **Problem.** Collection dedup catches identical URLs and identical normalized titles, but not several outlets writing different headlines about one incident. Those scatter, because scoring keys on terms rather than events: measured on three real headlines for one incident, 8.0 / 8.0 / 1.0 — the 1.0 being the only one that named the affected town.
- **First implementation failed in production and was rebuilt.** It passed a synthetic 204-article test, then produced a single 520-item group on 1,432 real articles. Causes were design, not tuning: transitive clustering chained unrelated items, and treating low document frequency as "distinctive" discarded the strongest evidence, since a heavily-covered incident puts its key term in many titles.
- **Shipped design.** Head-anchored greedy clustering — an item joins a head it directly resembles or starts its own, so chains cannot form — scored by IDF-weighted Jaccard over titles with the publisher suffix stripped.
- **Four guards:** no transitivity; a floor on shared information (`min_evidence`) so formulaic advisory titles that overlap heavily but say nothing distinctive do not cluster; `max_group_size`, past which a cluster is treated as template-matching, dissolved, and reported in the header; and `max_group_display`, bounding how much of the report one group can occupy.
- **Display only.** No score changed, no item merged, no item dropped. A grouped item below the cut is pulled up and marked *rescued from drop list* while remaining listed in the drop list, cross-referenced.
- **Deterministic output.** Score ties are common and grouping anchors on the first member seen, so ordering now breaks ties on title then URL. Repeated runs over the same corpus are byte-identical.
- **Verification.** `tests/grouping_test.py` — 13 checks against **29 hand-labelled real titles from the corpus that broke v1**, embedded in a scaled background so the weighting behaves as it does in production. Precision **1.00**, recall **0.75**; the hard negative (a different California city cyberattack with its own emergency declaration) stays separate; oversized clusters dissolve. Scorer parity **514/514 PASS**, recency **PASS**. End-to-end over 1,432 articles in 0.3s.
- **Config:** `scoring.settings.grouping` — `enabled`, `similarity`, `min_shared_tokens`, `min_evidence`, `max_group_size`, `max_group_display`.

## [2026-08-11] Staging doc enlarged; restraint doctrine scoped to the distributed product

- **The staging doc is now a review surface with its own, larger target.** Previously the docs carried a single "5–8 items per edition" rule that applied to everything, which produced only 2–3 items per section on the Monday draft — 5–8 spread across three content sections is 2–3 each by arithmetic. **Staging target is now ~5–6 per content section, ~15–18 total.**
- **"Restraint is the product" now explicitly governs the DISTRIBUTED product only.** The Thursday finished report stays at **5–8 items total**. The count narrows through the week, and that funnel is the stated intent rather than slippage. This ambiguity is corrected in `cti/pnd.md`, `cti/mandate.md`, `cti/codex.md` and the README tenet.
- **Standards are unchanged.** The additional staging entries are the next-lower-ranked items from the *same* sorted queue — lower tier and/or fewer elevation signals, not weaker sourcing. Extending the cut line down a ranked list is not relaxing the bar. Every staging entry still carries its scoring reasoning (tier + which multipliers fired) so the analyst can audit where the cut falls.
- **Config keys renamed for the distinction:** `production.item_target` → `production.staging_item_target` `[15, 18]`, `production.staging_per_section` `[5, 6]`, `production.distributed_item_target` `[5, 8]`. Safe because no engine reads them — `arbites.py` takes only `report_title` from this block.
- **No engine or scoring change.** `scoring.settings.surface_n` stays at 55, already ~3× the new staging target. Verified: scorer parity **514/514 PASS**, recency gate **PASS**, config loads, 50 sensors intact. The only edit under `core/` is a docstring in `pnd.py` naming the renamed keys.

## Initial release

A domain-agnostic OSINT collection-and-triage apparatus.

- **Domain-agnostic engine.** All logic lives in `core/` (`acolyte` collector, `arbites` scorer, `rules` matcher/scorer, `pnd` config loader). The engines hold no domain knowledge; each domain supplies a single `pnd.md` (manifest + sensors + scoring + production).
- **Collector (Acolyte).** RSS/Atom + page collection, full-text extraction (trafilatura), URL-hash **and** normalized-title deduplication, dated JSON corpus, push to a corpus store via rclone. Runs unattended on a systemd timer.
- **Pre-filter / scorer (Arbites).** Config-driven multiplicative scoring (tier weights × elevation multipliers) with a wide cut (~55 surfaced), a mandatory drop list, and visible per-item reasoning. No API — local scoring only.
- **Recency gate.** Flags items whose *publication* date falls outside the cycle window as "STALE — confirm current hook"; never drops them (preserves legitimately-current re-emergences).
- **Single-file P&D.** A domain's entire configuration — feeds, scoring model, output shape — lives in one `pnd.md`. Adding a domain is: drop in `<domain>/pnd.md` and run `run.sh <domain>`.
- **CTI effort (operational).** An SLTT cyber-threat-intelligence cycle: 48 trusted national/sector feeds at initial release, a convergence-based scoring model, and a staged weekly brief. Tuned as an example for a California SLTT AOR.
- **Second-domain support.** The engine is domain-agnostic by construction; a second effort needs only its own `pnd.md`.
- **Verification.** A parity test proves the config-driven scorer reproduces the original hardcoded logic exactly; a recency test covers the publish-date gate.
