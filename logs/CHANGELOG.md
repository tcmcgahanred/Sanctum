# Changelog — Sanctum

Notable changes to the Sanctum intelligence apparatus. **Git is the source of truth**; this file is the curated-highlights layer and `git log` is the full record. Brief editions (Vox) are keyed by distribution date (`vYYYYMMDD`), separate from code versioning.

## [2026-08-19] Three dead sensors removed, each diagnosed to a cause

First full health check from the collector host. 50 sensors in, 47 returning items, 3 not — and one that had been reported dead was healthy.

- **A status code proved nothing, exactly as designed for.** All three failures returned 200 or followed a redirect cleanly. Only the item count exposed them.
- **Packet Storm** — the site moved to a new domain and every feed path 404s there, including on its dedicated feed host. Already at 1 new in 9 runs before the move.
- **Full Disclosure** — reachable, but not by this collector. `curl` gets 200 from the same host on the same machine; `feedparser` gets connection-reset every time, under its default user agent and three others. The difference sits below the user agent, in the HTTP client itself. **Recorded rather than fixed:** swapping the fetch layer is not worth it for one sensor, and the point of writing it down is so nobody repeats the user-agent experiment. A genuine loss.
- **MS-ISAC advisories** — broken at the publisher. Returns 200 with an "Object moved" stub pointing at a Sitecore internal URL, and that target serves a web application rather than a feed. **MS-ISAC coverage survives** through the sibling alert feed, which returns proper RSS. This one had been claiming active AOR-relevant coverage while serving an HTML stub, which is precisely the failure the health check was built to surface.
- **Fortiguard was reported dead and is not.** The incoming handoff recorded it at HTTP 500 with an HTML error page; from the collector host it returns 50 items behind a 302 to a Fortinet file store. **Nothing was removed on the strength of that report.** Diagnose before deleting — a sensor removed on a guess is one someone re-adds next year.
- **MSRC returned 4,912 items in a single fetch**, around three quarters of everything pulled. It is not publishing 4,912 new articles; it serves its whole catalogue every time and dedupe reduces it to a handful. That is the gap between *returned* and *new* made visible, and it explains the old "52.7% of the corpus" figure — the first fetch saved the entire catalogue as new. Standing decision to leave it alone and watch is unchanged.
- **Reasons recorded in `cti/mandate.md`** alongside the previously dropped sensors, each with its diagnosis and, where relevant, what would have to change to bring it back.

## [2026-08-19] Sensor health: count the items, not the status code

Findings from the S2 domain's first five cycles. Two of the four requests were corrected before building — one would have fixed nothing.

- **A sensor can be configured, listed, and contributing nothing, with no error anywhere.** The run completes, the item count is quietly lower, and the sensor list claims coverage that does not exist. Three live examples, none detectable at the time: a feed redirecting to a host behind bot protection, one returning HTTP 500 with an HTML error page, and Packet Storm — which **returns 200 and serves a webpage**. Any check that trusts the status code passes it.
- **Per-sensor counts already existed and were counting the wrong thing.** `acolyte.py` logged `"<url> -> N new"`, where N is articles kept *after* the already-seen filter. A feed returning fifty items you have all seen logs `0 new`, identical to a dead one. The number that separates them — how many items the source returned at all — was computed on every run and discarded. **Second time a count without its denominator has misled here**; the first was match-frequency in the archive search. When reporting a count, report what it is out of.
- **The silent reclassification is the actual mechanism.** A feed parsing to zero entries returned `None`, and the caller fell through to the page-collection path without comment. A broken feed stopped being a broken feed and quietly became "a page source that yielded nothing." It still falls through — sometimes a page is genuinely the right path — but it now says so.
- **`status`, `bozo`, `bozo_exception` and the post-redirect URL were free on every parse and thrown away.** All four are now logged. Zero items returned is reported as a warning, printed as well as logged, with a closing line stating that zero items is not the same as zero new.
- **The redirect request was declined — the diagnosis was wrong.** feedparser already follows redirects. Tested against a known 301: it followed, reported `status: 301`, and exposed the final URL. The failing sensor's problem is the 403 at the destination, not an unfollowed redirect. Building redirect-following would have fixed nothing while appearing to fix something.
- **`tools/sensor_check.py`** — fetches every sensor a domain declares and reports items, status, redirect chain, parse result and a verdict. Items first: a feed flagged malformed can still yield usable entries, and a first crude pass over the CTI sensors produced three false alarms that way — a byte-order mark, rate-limiting caused by the probing itself, and a suppressed status header.
- **A guard found by using the tool on itself.** Run from a sandbox behind an egress proxy, all four sensors returned an identical 403 including two that are certainly healthy. Read literally, that output says "delete four working feeds." The tool now detects a uniform failure across every sensor and says so — the problem is the machine you are running from, not the sensors.
- **The multiplier ceiling check, and the arithmetic that prompted it.** A domain documented its stack as 4.9x; six signals at 1.5/1.5/1.3/1.3/1.3/1.3 actually multiply to **6.43x** — five factors had been multiplied instead of six. A floor-tier item with every signal then outranked every tier-2 and tier-3 item in the cycle. `vocab_check.py` now computes the product and compares it to the gap between the top tier and the one two steps down: past that, relevance has stopped ordering the queue. **It flags the mistaken 4.94x figure as an error too** — the check does not depend on anyone getting the arithmetic right first. CTI sits at 3.80x against a two-step gap of 4.0, so it warns rather than fails: inside the line, but one more multiplier crosses it.
- **A group's own name used as a term** is now flagged. Harmless at runtime, misleading on review — it inflates the term count and reads as real coverage. Eight were found in one domain, including one group's name sitting inside a different group.
- **Two design lessons written into `VOCABULARY.md`, both learned by reading output rather than by any check.** A group mixing specific designations with category nouns will surface your own side's stories while passing every automated test — a designation says whose thing it is, "system" does not. And bare co-occurrence across a whole article body is barely a condition: observed false positives matched one generic word and one platform word paragraphs apart. Proximity is now the documented default for multi-group conditions.
- **Proximity's three unguessable behaviours are documented at last.** It searches the body only and never the title; it tests only the first occurrence of each anchor-side term; and the anchor side has no word-boundary protection while the other side does. That last one bit in production — a term safe under boundary matching became unsafe on promotion to an anchor. Any group moved to the anchor side needs its collisions re-audited from scratch.
- **One request was already closed.** Per-group corpus filtering and match-frequency tracking shipped as `core/lexicanum.py` on the 17th; the handoff was working from stale information.
- **Verification.** Parity `PASS`. All six suites green. Six new checks on the guard, including one asserting the miscalculated stack would have been caught. `sensor_check.py` exercised against live feeds, which is how the uniform-failure guard was found.

## [2026-08-17] `DOMAINS.md` — what a domain folder is, and who owns which fact

- **The engine requires exactly one file from a domain: `pnd.md`.** Nothing in `core/` opens anything else in a domain folder. That was already true and nothing said so, which meant `cti/` was being read as a template when it is actually one domain's history — design and accident mixed together, with no way to tell which was which.
- **The folder contract, written down.** `pnd.md` required; `vocab.md`, `README.md`, `decomposition.md`, `mandate.md` expected; `policy.md` and `editions/` optional and only for domains that produce a product. A domain terminal at the staging document needs neither. A domain with only `pnd.md` runs — it is not wrong, just undocumented, and whoever inherits it pays.
- **The more damaging gap was ownership, not the file list.** A fact recorded in two documents gets updated in one of them. That is not hypothetical — it is what produced a roadmap describing a corpus that had not been transient for months, a `.gitignore` comment saying the same, and a README describing a private remote that had been public since publication. `DOMAINS.md` now assigns one home per fact, with a one-line test: **change a value in `pnd.md`; does any other file now contain a lie?**
- **Three violations found in CTI and recorded rather than fixed quietly.** `codex.md` Layer 3 restates the tier weights and multiplier factors that live in `pnd.md` — the same eight numbers in two files, so tuning the config silently makes the Codex wrong. That one is old. **The other two are mine, from this morning:** Layer 5 and the Mandate's Production block both reproduce Vox Policy §7 rather than referencing it. Both copies name the policy as authoritative and carry a date, which bounds the damage, but it is the pattern the rule forbids. Fix on next touch; nothing currently disagrees.
- **The suspected overlap was not the real one.** `codex.md` versus `decomposition.md` looked like duplication and is clean — `decomposition.md` declares its own boundary and restates the requirements only as tree roots. The actual duplication was between the Codex and the config.
- **`_template/` added** — five files, all neutral, carrying the reasoning as comments rather than as blanks to fill: why the collection window must match the real pull interval, why an empty group is worse than a missing one, why terms must not be written with padding spaces, why the surface has no target, why each group needs a review date *at creation* rather than added later as a guess.
- **A leading underscore means "not a domain."** Without the convention `_template/` is swept up by domain discovery and reported as a permanently broken domain, since its groups are deliberately empty — and a guard that always fails is a guard people learn to ignore. Applied in `tools/vocab_check.py`, with a test.
- **Verification.** Vocabulary gate reports `across: cti` only, exit 0 — the template is correctly invisible to it. All suites green; parity unchanged.

## [2026-08-17] `VOCABULARY.md` — the word lists get a method and a guard

- **Vocabulary was the highest-leverage unexamined part of Sanctum.** Scoring is visible and gets argued about; word lists are typed once and never read again. Every failure mode is silent — a stale group still matches *something*, so it looks like it works, and detecting the problem means noticing an absence. The method and the checker both exist to turn that invisible failure into a visible one.
- **Method extracted from a completed domain build in another session, not invented here.** The triage rule (*drop a noisy term only when an exact synonym exists; where none does, keep it and accept the noise*) and the placement principle (*a term's disruption cost depends on where it sits*) are marked VALIDATED because they were derived from real use. Indicator-derivation is marked **RECOMMENDED, NOT VALIDATED** and stays that way: two domains now hold a requirements decomposition, and neither validates the method, because both enumerated their terms first and wrote the decomposition afterward. Having the artifact is not having used the procedure.
- **A fifth row added to the placement table: force-surface.** Every other position is subject to the score — a noisy term in a tier promotes junk, but the threshold and the ordering still push it down. A noisy term inside a force-surface rule is immune to all of it by design, because overriding the score is what the rule is for. It is now documented as the highest-cost position in the system, and terms entering one get the strictest collision review.
- **The granularity tension does not bind Sanctum, and the method says so.** The received wisdom is that splitting a group later loses the history, so granularity must be settled up front. That assumes matches are recorded at collection time. `core/lexicanum.py` records nothing and recomputes on demand, so a group invented this morning runs against everything collected last year. Splitting is reversible and scoring was already indifferent — the mechanism deliberately does **not** force the question at build time. It holds only while the corpus is retained, so `.gitignore`'s stale *"transient 7-day corpus"* comment was corrected: retention is now documented as load-bearing.
- **`tools/vocab_check.py` — six checks, wired into the commit gate.** Orphaned boundary terms, redundant boundary terms, padded terms, empty groups, dropped-but-still-live terms, and group staleness. It found real defects on its first run against CTI.
- **Seven of CTI's eleven boundary entries were dead.** `hack`, `leak` and `war` matched no live term in any group — the terms they guarded had been removed at some point and the entries outlived them, which reads to a later reviewer as evidence those terms are still there. `ics`, `grid`, `uc` and `csu` are four characters or fewer, where the matcher already applies boundaries automatically. All seven removals are provable no-ops and **parity confirms not one score changed**.
- **A defect nothing else would have caught: `" calif "` does not do what it looks like.** The padding reads as an attempt at word-boundary matching. `core/rules.py` strips every term before matching, so it becomes the bare 5-character substring `calif` — above the auto-boundary length, so it falls back to substring matching, the exact behaviour the spaces were meant to prevent. Verified: it matches *"califon new jersey"*. Recorded rather than fixed; both clean fixes change matching, which makes it a Planning & Direction decision.
- **Accepted findings are downgraded, never silenced.** A guard nobody can satisfy is a guard people route around, and here the route around is `--no-verify`, which would disable the scrub check too. A finding the domain has consciously accepted is recorded in `vocab.md` with a reason and a date, prints on every run as ACCEPTED, and stops blocking. Staleness is a warning for the same reason — a date passing is a reason to look, not a reason to block a commit.
- **Two files per domain, and the split is the point.** `pnd.md` holds the terms and stays the single source of truth. `<domain>/vocab.md` holds the *reasoning* — version history, collisions, dropped terms and why, per-group review dates, known gaps. It never repeats the term lists, because two copies of the same words drift within a month and the copy nobody runs is the one that gets edited.
- **`cti/vocab.md` records three open findings, all left for P&D.** The `incident` group covers confidentiality only — checked against MITRE ATT&CK's Impact tactic, none of its 15 concepts have a matching term, so a DDoS taking a county's 911 line offline does not register as an incident and force-surface rule M1 never fires. `geo` carries four documented county-name collisions and was just wired into M1, the highest-cost position. And `" calif "` above.
- **Verification.** Parity `PASS` on 514 real + 500 fuzz articles. All six suites green. New checks on the guard itself are written against synthetic domains — a test bound to a live word list starts failing the day someone edits it, which trains people to ignore it.

## [2026-08-17] `EXPLOITATION.md` — stage 3b written down for the first time

- **Every part of Sanctum was version-controlled except the one doing the most visible work.** Sensors, scoring model, collection window — all config. But the step that turns ~55 ranked candidates into a readable vox lived only as accumulated instruction inside one operator's chat. A different operator, or a different model, produced a different vox from identical input. Clone the repo and you got collection and triage but not the thing that made the output good.
- **The method was extracted, not invented.** The rules were read out of a vox already judged good. Several were already declared in that document's own header — *"PRODUCTION STANDARDS APPLIED: impact/attribution claims stated only as far as sources confirm…"* — and the rest were being applied consistently without ever being recorded. Deriving from a known-good artifact beats guessing at requirements.
- **Eleven rules, domain-agnostic.** Actionable relevance clause per item; claims never stated more strongly than the source; **marginal items kept and flagged rather than dropped** (tenet 8 carried into the exploitation layer); product-specific items name the product; dated source plus verification state; score and reasoning carried through; jargon explained in-line; one event one entry; serialised IDs ordered by requirement priority; the document declares its own recency window and collection gaps; no handling markings.
- **R6 answers the weights request.** Each item carries its 3a score with the tier and multipliers behind it, plus a legend of the domain's scoring model generated from `pnd.md` so a reader who has never seen the config can interpret the numbers. Stated once in the header: *a score is an ordering aid, not a measurement.* The purpose is to let the team argue with the **ranking**, not just the content — and the ranking is the part Planning & Direction actually controls.
- **3b is documented as the second gate, not polish.** 3a scores on terms, so it surfaces items that match well and matter little — a foreign government breach with no local nexus scores like a local one. In the reference vox, 3a surfaced exactly that and 3b caught it. Framing 3b as a finishing touch would have produced a specification too loose to catch it again.
- **Domain-specific parts moved into config**, same split as everything else: `cti/pnd.md` `production` now declares `audience`, `relevance_clause` and `show_scores`. The method file holds no domain knowledge.
- **Tenet 7 holds.** Nothing in `core/` calls a model. Sanctum ships the method; the operator brings the tool and the judgement, and decides every item.
- **R5 now requires a working link, not a citation.** The reference vox named its sources but carried no URLs. R2 asks the reader to trust a claim only as far as its source supports it, and R5 tells them what to verify against — neither is possible from a citation they cannot open. **3a already carries every URL through**, so the loss was introduced at 3b, not missing from the input. Sources are now dated markdown links, one line each where an item has several.
- **Every vox is committed to `<domain>/editions/`.** It is the domain's record of what was actually put out, and the only way to answer "what did we say in August?" later. Sanctum cannot automate it — the vox does not exist until a person has made it, so there is no run that could push it. Documented as a deliberate human step at the end of 3b, with the commands. The commit gate runs on the way through, which matters: a vox is written from external reporting and is the likeliest place for something unintended to arrive.
- **R11 — names come from the domain file, exactly.** Two documents exist and neither may borrow the other's word. `deliverable_name` `WCTI_v[YYYYMMDD]_STAGING` → **`_VOX`**: the file shared with the team was named after the document nobody reads. `report_title` is now explicitly the staging document's title, and a new `vox_title` gives the vox its own. The rule also forbids inventing prefixes at production time — the reference vox arrived carrying an organisation's initials that appear nowhere in the config. If something belongs in a name it belongs in the config, where every future edition picks it up; a name invented during production is a name that changes between operators.
- **Verification.** Config loads with the new production keys, 50 sensors and all 8 groups intact, full suite passes including 1,014-article scorer parity. No engine code changed.

## [2026-08-17] Taxonomy settled: Sanctum is stages 1–3, and its output is the vox

- **The vox is not an intelligence product — it is a refined staging document.** Everything in it is *exploitation*: items selected from candidates, reporting summarised into readable prose, source caveats (*"claims under investigation, do not state as confirmed"*), triage notes (*"out-of-scope geography, likely cut"*), section assignment. None of it is assessment. The document says so itself — *"a REVIEW SURFACE, not the finished product."* An earlier revision of both diagrams filed the vox as a stage 4 output. That was wrong.
- **Settled scope: SANCTUM IS STAGES 1–3.** Planning & Direction configures, Collection gathers, Processing & Exploitation scores *and then refines*. Output is the vox. **Stages 4–6 are not Sanctum.** After Monday morning any involvement with the vox is ad hoc and operator-directed.
- **Stage 3 has two halves, and only one is code.** *3a mechanical* — Arbites and rules.py score and rank, deterministic and config-driven. *3b linguistic* — select, summarise, caveat, section. 3b cannot be expressed as keyword rules; "judge whether a low-maturity county IT shop should care, and say why in two sentences" is not a matcher. It is currently performed by an operator with an LLM, and **it is the one part of the apparatus not written down anywhere.**

## [2026-08-16] Lexicanum — archive search and match-frequency over time

- **The corpus was write-only.** Sanctum scores each cycle independently and then forgets, keeping every article permanently while offering no way to ask the archive a question. Trend is the stated reason for retaining everything, and it was the one thing the tooling could not do.
- **The workflow being replaced was manual.** Bulk keyword search across a pile of documents, hits pasted into a spreadsheet with a column naming the term that matched. The term was not a filter but an **index** — a handle to pull later. Question one: *where has this appeared?* Question two follows immediately: *is it actually spreading, or is one event being re-reported?* Those call for different responses. Search and counting are the same feature, which is why they shipped as one engine rather than two.
- **`core/lexicanum.py`** — searches the whole archive by keyword group or ad-hoc term and reports a per-period series alongside the items behind it. `--group` (repeatable), `--all-groups`, `--term`, `--since` / `--until`, `--by day|week|month`, `--by-published`, `--counts`, `-o`, and `--pnd` for out-of-tree domains.
- **Matches are recomputed on demand, not stored at collection time.** This is the design, not a shortcut. A stored index can only answer questions you thought to ask on collection day; because full text is retained and the matcher is deterministic, **a group invented this morning runs against everything collected last year** — including terms for a system nobody was tracking when the articles arrived. It also guarantees results agree with the scorer: same matcher, same word-boundary rules, same scopes, no second implementation to drift. Verified by test.
- **Reports a RATE, not a bare count — added after the first real run nearly misled.** Weekly ransomware hits fell 475 → 122, which read as a collapse. Article volume that week had fallen 6,585 → 1,370, so the rate had actually *risen*, 7.2% → 8.9%. Counts alone said the opposite of the truth. Every table now carries the period's article total as an `of` column and a `rate` column, the bar tracks rate rather than hits, and collection volume per period is stated once at the top. Regression-tested with the same shape at small scale: 20 hits of 100 versus 2 of 10 — a 90% apparent collapse at a flat 20% rate.
- **Bucketed on collection date.** Publication dates are missing or malformed often enough that the scorer carries an entire recency gate to cope; bucketing on a frequently-absent field would produce a clean-looking chart built on guesses. Each hit still shows its publication date, and `--by-published` switches axis, falling back per-item and reporting how many items it had to fall back on.
- **Reports counts, never conclusions** (tenet 9). The header states plainly that reporting volume is not activity — a quiet week for a publisher looks identical to a quiet week in the field. Every count is backed by a listable item, so no number appears that cannot be drilled into (tenet 8). A group with zero hits is reported as zero rather than omitted: mistargeted and genuinely quiet are different findings and both are worth seeing.
- **Groups with no hits are the staleness signal.** This supersedes the separate vocabulary-staleness request, which asked for a review-date flag. A group that has matched nothing across many cycles is empirical evidence of decay, where a calendar date is only a reminder.
- **Read-only.** It writes nothing to the corpus, changes no score, and is not part of the weekly cycle — it runs when asked.

## [2026-08-16] Exclusion operator — "match X unless Y"

- **Deleting a noisy term silently deletes the requirement it stood for.** With no way to express an exception, the only cure for a term that collides with an unrelated meaning was to remove it. Threat-actor names are the standing example: several are also ordinary products, places, or common words, and they arrive through general feeds that are otherwise wanted — so dropping the *source* was not available either. Every collision so far was resolved by finding a more precise synonym; where none exists, the choice was accept the noise or lose the requirement. This is the third option.
- **`not` added to the rule grammar.** `{all: [{group: X}, {not: {group: Y}}]}`. Composes with `any`, `all`, `proximity` and itself; usable in tier rules and multipliers alike.
- **Narrow, deliberate exception to tenet 8** ("prefer false positives — flag, don't drop"). Exclusion removes nothing: it withholds a tier or a multiplier, so an excluded item is still collected, still scored, still listed in the drop list, and still shown with its reasoning — just lower. Tenet 8 in the README now records this explicitly.
- **A satisfied exclusion names itself in the scoring reasoning** (`not medical`), because an auditor reading a score needs to see that the exclusion fired, not merely which terms hit.
- **Config validation recurses into `not`.** A typo inside an exclusion would otherwise reference a group that does not exist, match nothing, and silently switch the exclusion off — letting the noise back in with nothing on the page to say so. Unknown groups inside `not` now fail at load.
- **Verification.** `tests/upgrades_test.py` — a name collision resolves correctly, double negation and nesting behave, the excluded article falls to the floor rather than disappearing, and **a config containing no `not` scores exactly as before**. Backed by the full parity suite: **514/514 real articles and 500 fuzz articles match the pre-change engine exactly**, so no existing edition moves.

## [2026-08-16] Tenet 3 rewritten; domain files enforced inert

- **Tenet 3 was about the wrong thing.** "Config over code — steer by editing `pnd.md`, never by editing Python" named a *file format* when the property that actually matters is *separation*: the engines learn nothing about a domain, so a new domain is a drop-in and performs the same as any other. Format was never the point; it was one way of protecting the point.
- **Rewritten as the guardrail it always was.** Tenet 2 now states the goal (domain-agnostic engine, same performance on any domain). Tenet 3 states the constraint that preserves it: *domain files declare, they never behave* — settings and the explanation of those settings, nothing else.
- **Why this came up.** Moving domain files from YAML-inside-markdown to Python puts each explanation directly against the setting it describes, instead of in a prose section that drifts away from it. That drift is not hypothetical here: a wrong explanation of a dead sensor once propagated into three documents at once. The gain is real, but YAML's inability to express logic was also an accidental guard, and Python hands that ability back.
- **So the tenet no longer relies on discipline.** `tests/domain_check.py` parses each domain file and refuses anything that is not inert data: imports, functions, classes, conditionals, loops, calls, lambdas, comprehensions, attribute access, subscripting, f-strings, arithmetic, and references to names not defined earlier in the same file. Permitted: literals, nestings of literals, comments, a docstring, and a reference to a value assigned above — so a shared term list is defined once rather than retyped into two groups that later disagree.
- **Deliberately stricter than necessary.** Some refusals are harmless in isolation — joining two lists with `+` computes nothing dangerous. Strictness is cheap to relax when a real need appears and expensive to reimpose after a domain file has grown a brain (tenet 10).
- **Messages are written for a non-programmer**, because whoever stands up a domain should not need to be one: *"a condition makes the file act differently in different situations."*
- **`core/pnd.py` is excluded by name.** It is the engine that *loads* domain files and is legitimately full of logic — same filename, opposite meaning.
- **New commit gate.** `tests/pre_commit.sh` now runs both guards (scrub, tenet 11; domain, tenet 3) and is what gets installed as the hook; `scrub_check.sh` is no longer installed directly. Both guards run even when the first fails, so one commit attempt reports everything wrong at once.
- **Verification.** `tests/domain_check_test.py` — a realistic clean domain file passes untouched, and **28 forms of behavior are refused**, including three nested inside literals, each with a plain-language reason. Discovery over the live repo correctly finds `cti/pnd.md` (skipped: YAML cannot express logic) and correctly ignores `core/pnd.py`.
- **No engine change and no domain file converted.** This lands the guardrail first; the markdown-to-Python migration is a separate, later change that this makes safe.

## [2026-08-13] Same-event grouping in the staging report

- **Problem.** Collection dedup catches identical URLs and identical normalized titles, but not several outlets writing different headlines about one incident. Those scatter, because scoring keys on terms rather than events: measured on three real headlines for one incident, 8.0 / 8.0 / 1.0 — the 1.0 being the only one that named the affected town.
- **First implementation failed in production and was rebuilt.** It passed a synthetic 204-article test, then produced a single 520-item group on 1,432 real articles. Causes were design, not tuning: transitive clustering chained unrelated items, and treating low document frequency as "distinctive" discarded the strongest evidence, since a heavily-covered incident puts its key term in many titles.
- **Shipped design.** Head-anchored greedy clustering — an item joins a head it directly resembles or starts its own, so chains cannot form — scored by IDF-weighted Jaccard over titles with the publisher suffix stripped.
- **Four guards:** no transitivity; a floor on shared information (`min_evidence`) so formulaic advisory titles that overlap heavily but say nothing distinctive do not cluster; `max_group_size`, past which a cluster is treated as template-matching, dissolved, and reported in the header; and `max_group_display`, bounding how much of the report one group can occupy.
- **Display only.** No score changed, no item merged, no item dropped. A grouped item below the cut is pulled up and marked *rescued from drop list* while remaining listed in the drop list, cross-referenced.
- **Deterministic output.** Score ties are common and grouping anchors on the first member seen, so ordering now breaks ties on title then URL. Repeated runs over the same corpus are byte-identical.
- **Verification.** `tests/grouping_test.py` — 13 checks against **29 hand-labelled real titles from the corpus that broke v1**, embedded in a scaled background so the weighting behaves as it does in production. Precision **1.00**, recall **0.75**; the hard negative (a different California city cyberattack with its own emergency declaration) stays separate; oversized clusters dissolve. Scorer parity **514/514 PASS**, recency **PASS**. End-to-end over 1,432 articles in 0.3s.
- **Config:** `scoring.settings.grouping` — `enabled`, `similarity`, `min_shared_tokens`, `min_evidence`, `max_group_size`, `max_group_display`.

## Initial release

A domain-agnostic OSINT collection-and-triage apparatus.

- **Domain-agnostic engine.** All logic lives in `core/` (`acolyte` collector, `arbites` scorer, `rules` matcher/scorer, `pnd` config loader). The engines hold no domain knowledge; each domain supplies a single `pnd.md` (manifest + sensors + scoring + production).
- **Collector (Acolyte).** RSS/Atom + page collection, full-text extraction (trafilatura), URL-hash **and** normalized-title deduplication, dated JSON corpus, push to a corpus store via rclone. Runs unattended on a systemd timer.
- **Pre-filter / scorer (Arbites).** Config-driven multiplicative scoring (tier weights × elevation multipliers) with a wide cut (~55 surfaced), a mandatory drop list, and visible per-item reasoning. No API — local scoring only.
- **Recency gate.** Flags items whose *publication* date falls outside the cycle window as "STALE — confirm current hook"; never drops them (preserves legitimately-current re-emergences).
- **Single-file P&D.** A domain's entire configuration — feeds, scoring model, output shape — lives in one `pnd.md`. Adding a domain is: drop in `<domain>/pnd.md` and run `run.sh <domain>`.
- **CTI effort (operational).** An SLTT cyber-threat-intelligence cycle: 48 trusted national/sector feeds at initial release, a convergence-based scoring model, and a staged weekly brief. Tuned as an example for a California SLTT AOR.
- **Second-domain support.** The engine is domain-agnostic by construction; a second effort needs only its own `pnd.md`.
- **Verification.** A parity test proves the config-driven scorer reproduces the original hardcoded logic exactly; a recency test covers the publish-date gate.
